# 猩红山脚下 · State 初始化与玩家常量宏

> 状态：V2 建议稿。  
> 配套文件：`状态初始化.yaml`  
> 已使用 Loom Studio 的 `parseCardStateConfig`、`validateStateContribution`、`materializeStateContribution` 和 `renderVariableMacros` 验证。

---

## 0. 这次改动的核心

玩家的这些东西，确实更接近“故事开始后不再变化的身份常量”，而不是普通运行态变量：

- `pronouns`
- `city`
- `trait_1` / `trait_2` / `trait_3`
- `negative_trait`

因此 V2 把这组数据从“挂在玩家 Entity 上的 `survey` 组件”改为：

```text
player.constants
```

即一个 Timeline State 顶层绑定。

这样做的好处：

1. 宏路径相对短，适合直接写进 Prompt：
   ```text
   {{timeline.player.constants.pronouns}}
   {{timeline.player.constants.city}}
   {{timeline.player.constants.trait_1}}
   {{timeline.player.constants.trait_2}}
   {{timeline.player.constants.trait_3}}
   {{timeline.player.constants.negative_trait}}
   ```
2. 不占用、不修改 Loom Studio 内置的玩家资料组件；
3. 与 NPC 的“运行态变量”明确分开；
4. 以后即使 NPC 结构、关系值或地点结构变化，玩家常量路径仍可以保持稳定。

---

## 1. Loom Studio 的宏约束

Loom Studio 的 State 宏来自 State 快照中的**标量叶子节点**。

当前支持：

- string
- number
- boolean
- null
- 嵌套 object 的路径

不支持直接把 array 或 object 作为宏输出。例如：

```text
{{timeline.player.constants.traits}}
```

如果 `traits` 是数组，不会被替换，还会产生 `variable.value_not_scalar` 诊断。

因此 V2 不再把三项特质存成数组，而是拆成三个标量：

```text
trait_1
trait_2
trait_3
```

这正好满足“三项特质作为宏稳定提供 Prompt”的需求。

> 注意：State Schema 本身没有 `readOnly` 或不可变标志。  
> 这里的“常量”是作者与 Agent 的约定：初始化写入一次，之后不随剧情修改。  
> 如果以后需要硬性只读保护，需要扩展或专用写入逻辑，而不是普通 State Schema。

## 3. 玩家常量

### 3.1 路径

```text
player.constants
```

模板：`player.constants`  
绑定方式：`timelineStateBindings`

它不挂载到 `loom-player` Entity 上，而是作为顶层 Timeline 对象存在。  
原因是这些值是单例玩家常量，不需要 Entity / Component 结构，也不需要参与 NPC 关系系统。

### 3.2 字段

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `completed` | boolean | 开始前调查是否已经写入 |
| `pronouns` | string | 性别代词 / 性别认同 |
| `city` | string | 来自哪座城市 |
| `trait_1` | string | 第一项特质 |
| `trait_2` | string | 第二项特质 |
| `trait_3` | string | 第三项特质 |
| `negative_trait` | string | 负面特质 |
| `negative_trait_kind` | enum | `derived` / `pure` / 空字符串 |
| `negative_trait_source` | string | 若为 derived，记录来源正面特质；pure 时为空 |
| `background_notes` | string | 其他需要作为常量保留的背景信息 |

### 3.3 三项特质为什么拆成三个字符串

宏只能输出标量。因此：

- 不存 `traits: [{id,name}, ...]`
- 改为 `trait_1`、`trait_2`、`trait_3` 三个字符串

建议 Agent 写入时使用“名称 + 关键表现”的字符串形式，例如：

```text
非理性想象 / Irrational Imagination：想象猛烈且栩栩如生；能把不存在的事物讲得比现实更像真的；在绝境中，想象会为你打开一扇不合常理的门
```

这样宏直接输出时，Prompt 就能得到完整且稳定的特质信息，而不只是一个名称。

如果以后需要程序化判断特质 ID，可以再额外增加：

```text
trait_1_id
trait_2_id
trait_3_id
```

V2 暂不增加，优先保证 Prompt 可读性。

### 3.4 Prompt 宏示例

在 Preset / Lore / 角色卡提示词中可以直接写：

```text
## 玩家常量

- 性别代词 / 认同：{{timeline.player.constants.pronouns}}
- 来自城市：{{timeline.player.constants.city}}
- 三项特质：
  1. {{timeline.player.constants.trait_1}}
  2. {{timeline.player.constants.trait_2}}
  3. {{timeline.player.constants.trait_3}}
- 负面特质：{{timeline.player.constants.negative_trait}}
- 其他背景备注：{{timeline.player.constants.background_notes}}
```

`negative_trait_kind` 和 `negative_trait_source` 通常是给 Agent / 逻辑判断用的，不一定需要输出到 Prompt。

### 3.5 Agent 写入顺序

玩家提交开始前背景调查后，建议 Agent 按以下顺序写入：

1. 解析姓名、代词、城市、三项特质、一项负面特质。
2. 将三项特质分别写成 `trait_1`、`trait_2`、`trait_3`。
3. 写入 `negative_trait`。
4. 根据来源写入：
   - `negative_trait_kind: "derived"` 或 `"pure"`
   - `negative_trait_source`：derived 时填来源特质，pure 时填空字符串。
5. 写入 `background_notes`。
6. 最后把 `completed` 设为 `true`。
7. 此后这组字段视为只读，不再随剧情更新。

| `status` | enum | active / missing / dead / transformed / unknown |
| `current_goal` | string | 当前目标 |
| `notes` | string | 运行备注，不放隐藏剧透 |

人格轴：

```text
open, closed, bold, passive, insightful,
dull, reliable, unreliable, agreeable, adversarial
```

### 4.3 为什么 NPC 仍然是 State 变量

NPC 的以下内容会随剧情变化：

- 对玩家关系
- 当前目标
- 状态
- 运行备注

所以它们继续作为 `npc.profile` 运行态组件存在。

但 NPC 的完整秘密、真实背景和隐藏计划仍应留在 Lore / 角色文件中，不放进玩家可见的 State 面板。

## 8. 注意事项

1. **State 没有原生只读约束。**  
   `player.constants` 是“约定常量”。Agent Prompt 应明确要求它在初始化后不再修改。

2. **使用数组无法直接做宏。**  
   因此 V2 使用 `trait_1` / `trait_2` / `trait_3` 三个标量字符串。

3. **如果以后要短别名，需要额外机制。**  
   例如把 `{{timeline.player.constants.pronouns}}` 简写成 `{{player_pronouns}}`，原生 State 宏做不到；需要 Macro Provider 扩展或额外 Prompt 处理。

4. **修改 Schema 后要升级 `templateVersion`。**  
   `stateTemplates` 和 `timelineStateBindings` 中的版本必须同步。

5. **新增 NPC 需要同时增加两处。**  
   - `timelineStateEntities` 添加 Entity。
   - `timelineComponentMounts` 添加对应 `profile` 初始数据。

6. **State 面板对玩家可见。**  
   不要把 NPC 的真实秘密、未公开动机或隐藏计划放进 `npc.profile.notes`。
