# 开始前背景调查

> **文档状态：前期调研 + V1 需求记录。**  
> 本文用于记录《猩红山脚下》首楼表单在 Loom Studio 中的运行边界、数据去向与实现约束。  
> **V1 字段与数据流已经确认**，见第 0 节；正文其余部分保留为设计与实现依据。

---

## 0. V1 已确认需求

### 表单字段

1. **主角姓名**
   - 可留空。
   - 留空时使用 `{{user}}` 作为玩家档案名。
2. **性别代词 / 性别认同**
   - 单一自由文本字段。
3. **从哪座城市来**
   - 自由文本字段。
4. **特质 Traits**
   - 从七项特质中选择恰好三项：
     - 身强体壮 / Powerful Build
     - 神秘主义 / Mystical
     - 与动物交谈 / Talk to Animals
     - 街头智慧 / Street Smart
     - 洞察力 / Keen Eye
     - 书籍智慧 / Book Smart
     - 火辣 / Hot
   - 每项特质连同其列出的全部表现一起写入档案。
5. **负面特质 / Extremely Negative Traits**
   - 从已选择的三项特质中再选择一项。
   - 强化该特质对应的阴暗面，并随档案提交。
6. **固定故事开场白**
   - 作为首楼固定叙事前置内容。
   - 不进入表单生成的玩家档案。

### 数据流

```text
首楼固定开场白 + HTML 表单
  -> 玩家填写
  -> 生成纯文本 Markdown 档案
  -> 玩家复制并发送
  -> Agent 读取档案
  -> Agent 按当前 State Schema / 工具 / 授权写入 State
```

- 除固定开场白外，不使用 HTML 直接写 State。
- 纯文本档案是 V1 的事实来源。
- 如果 Agent 尚无明确的 State Schema、路径或写入授权，则先保留为文本上下文，不自行编造字段。
- V1 实现文件：`../开始前背景调查.html`。

## 1. 先给结论

1. **普通消息 HTML 不能直接提交到 Loom Studio 后端。** 首楼 HTML 运行在隔离 iframe 中，没有同源权限，也没有面向宿主业务数据的接口。
2. **首楼 HTML 可以做自包含表单 UI，但它最稳妥的“提交”方式是生成一段文本，让玩家复制并发送到对话输入框。** 这段文本会作为普通玩家输入进入会话历史，模型能读到它，但它本身不会自动变成 State、变量或玩家资料。
3. **如果表单数据必须持久化到 State，需要额外机制。** 例如 Agent 工具、带授权的扩展或 Loom Script；这会影响卡片分发、安装步骤、权限确认和兼容性，不能当作单个 HTML 文件自带的能力。
4. **Loom Studio 已有玩家资料（用户模板）只覆盖名称、描述和头像。** 它可以在新故事开始时复制到 Timeline State，并通过 `{{user}}`、`{{user.description}}` 等宏供开场白和提示词使用，但它不是本轮角色背景表单的通用数据容器。
5. **因此当前最合适的顺序不是先写字段，而是先决定数据去向。** 只有确定“一次性提示文本 / 玩家资料 / Timeline State / 扩展私有数据”中的哪一类，字段、验证和输出格式才有稳定依据。

## 2. 角色卡首楼在 Loom Studio 中如何工作

### 2.1 角色卡开场白

Loom Studio 的 Card 有开场白内容，支持默认开场与备选开场：

```text
card.opening.content
card.opening.alternatives[].content
```

正文保存为 Markdown 片段或完整 HTML 文档。完整 HTML 常见写法：

````markdown
```html
<!doctype html>
<html>...</html>
```
````

也支持直接以 `<!doctype html>` 开始的未围栏文档。Loom Studio 的消息解析会将其识别为一个独立 `document` 片段，再交给隔离 iframe 渲染。

### 2.2 首楼与第一条玩家输入

大致流程是：

```text
角色卡开场白
  -> 文本管线 / Display 投影
  -> Markdown 片段或 HTML 文档分段
  -> 消息内容渲染
  -> 玩家在输入框发送第一条叙事输入
  -> 进入 Timeline 的 user-input / Narrative 历史
```

所以，如果首楼里放一个“生成背景档案”的 HTML 表单，合理的用户体验是：

```text
玩家填表
  -> 表单在浏览器内生成一段 Markdown 文本
  -> 玩家复制这段文本
  -> 粘贴到输入框并发送
  -> 模型将其作为本次游玩的背景与约定读取
```

它不会在点击按钮时自动开启故事或自动写入角色 State。

### 2.3 宏在开场白中的位置

Loom Studio 在读取开场白和创建 Timeline 时，会用玩家资料、卡片数据和初始 State 变量渲染宏。因此首楼正文可能出现：

```text
{{user}}
{{user.description}}
{{char}}
```

但要注意：

- 完整 HTML 文档在消息渲染阶段不会再次做客户端宏展开；宏是在开场白进入渲染器之前处理的。
- 可安全依赖的主要是玩家资料、卡片静态宏，以及首楼生成时已有的变量。
- 不应假设首楼 HTML 表单能实时读取任意 Timeline State。
- 用户填写表单后产生的数据不会自动回写玩家资料或 State。

相关位置：

- `packages/application-runtime/src/cards/card.ts`
- `packages/application-runtime/src/runtime/narrative-runtime.ts`
- `apps/studio-client/src/app/use-studio-derived-values.ts`
- `apps/studio-client/src/features/message-content/ui/message-content.tsx`

## 3. 首楼 HTML 的实际运行边界

### 3.1 渲染方式

完整 HTML 文档进入 `HtmlPreview`，在 `sandbox="allow-scripts"` 的 iframe 中运行。没有 `allow-same-origin`，因此：

- 不能读取宿主页面 DOM；
- 不能借父页面 Cookie、LocalStorage、IndexedDB 等做持久化；
- 不能直接调用 Studio 的业务 API；
- 不能直接修改角色卡、玩家资料或 Timeline State。

### 3.2 内容安全策略

普通消息 HTML 使用的策略大致限制为：

```text
default-src 'none'
script-src 'unsafe-inline'
style-src 'unsafe-inline'
img-src data:
font-src 'none'
media-src 'none'
connect-src 'none'
frame-src 'none'
form-action 'none'
```

这意味着：

- 可以使用内联 CSS、内联 JavaScript、data URI 图片；
- 不能依赖外部字体、CDN、远程图片或网络请求；
- 原生表单提交会被阻止，按钮应使用 `type="button"` 或脚本阻止默认提交；
- 所有视觉和逻辑都应内嵌在同一个 HTML 文件里。

### 3.3 宿主通信

普通消息 HTML 与宿主之间只有尺寸测量消息，用于让 iframe 自适应高度。它不提供 State、玩家资料、AI、文件或通知的业务桥。

因此表单不能把结果“postMessage 给 Loom Studio 自动保存”。

### 3.4 状态生命周期

消息 HTML 是消息视图的一部分。离屏卸载、重新渲染或切换界面后，表单输入不保证恢复。官方文档也明确说过：

- 消息内表单、播放进度等局部状态不保证持久；
- 复杂、长期存在的界面应使用独立 Surface 或扩展界面；
- 不要把 iframe 卸载回调当作可靠提交时机。

对本项目的直接影响：

- 表单不能依赖自动保存；
- 应让玩家在填写后立即生成结果并复制；
- 如果字段较多，应提供结果预览和一次性复制；
- 如果确实需要长期保存，应改用扩展界面或其它持久化方案。

相关位置：

- `apps/studio-client/src/features/message-content/model/html-document.ts`
- `apps/studio-client/src/shared/iframe-runtime/frame-lifecycle.ts`
- `docs/architecture/ui/iframe-runtime.md`
- `docs/architecture/application/ui/README.md`

## 4. 项目里可能承接表单数据的机制

下面先列出现有机制及其边界，不代表最终字段设计。

| 机制 | 能保存或影响什么 | 首楼 HTML 表单能否直接使用 | 对表单设计的含义 |
| --- | --- | --- | --- |
| 首楼 HTML 自身 | 当前 iframe 内的 DOM 与 JS 状态 | 能显示、能收集、不能可靠持久化 | 适合做 UI 和生成文本，不适合作为数据库 |
| 会话消息 / 玩家输入 | 对话历史中的一段文本 | 玩家复制并发送后可以进入 | 最稳妥的第一版提交流程 |
| 玩家资料 `userProfiles` | 名称、描述、头像 | 只能通过宏预填，不能由普通 HTML 写回 | 适合承载少量身份信息，但不是通用表单容器 |
| Timeline State | 结构化、可分支、可撤销的运行数据 | 普通 HTML 不能直接写 | 适合需要持久化、变量面板、Agent 工具和分支一致性的数据 |
| Card State Template / Contribution | 新 Timeline 的初始实体、组件与默认值 | HTML 表单不能直接初始化 | 需要先由作者定义 Schema 和初始结构 |
| Card 静态宏 | 卡片作者配置的固定值 | 首楼中可读取 | 可放世界名、固定规则、预设选项，不是玩家输入 |
| Text Transform / Extractor | 显示或提示词投影、可产生提取结果 | 不能把提取结果自动变成 State | 不能当作表单提交后自动写变量的机制 |
| Loom Script / 扩展 | 可读 State、在特定运行环境写 State、注册 UI | 普通消息 HTML 不直接接入；需要安装、授权与 Mount | 若需要“提交后自动写 State”，这是候选路线，但复杂度高 |
| STBridge / EJS / MVU 兼容 | 导入部分 SillyTavern 内容与表达式 | 不能假定完整 ST 前端或表单运行时存在 | 若卡片还要兼容 ST，应优先采用纯文本输出方案并单独验证 |

### 4.1 玩家资料

新建故事时，玩家可以从用户资料模板中选择名称、描述和头像。启动后这些内容会成为 Timeline State 中的内置玩家资料：

```text
$loom.players.User.components.loom_profile
```

可通过以下宏读取：

```text
{{user}}
{{user.description}}
```

但用户资料模板只有 `name`、`description` 和可选头像，不是可任意扩展的表单模型。是否把“角色姓名、性别、外貌、背景”等塞进 `description`，需要单独决定。

### 4.2 Timeline State

State 是结构化 JSON，支持 Schema、Revision、分支、撤销和 Agent 工具读写。适合例如：

```text
角色属性
关系值
资源/物品
剧情旗帜
玩家偏好中被要求持久保留的部分
```

但 State 不是自动游戏规则系统，作者需要先定义：

- Entity Type；
- Entity；
- Component Definition；
- Component Template；
- 可选 Entity / Component Mount；
- 初始值与 Schema；
- 谁来写、什么时候写、失败如何处理。

另外，State 写入通常需要 Agent 工具、扩展或脚本；普通消息 HTML 不在这个权限链里。

### 4.3 Text Extractor

历史文本管线中存在 Extractor，可以产出 artifact，但产品方向已明确为：

- Extractor 不再是重点独立作者功能；
- 自定义提取由脚本处理；
- 跨组件共享的正式数据优先写入 State / 变量；
- 提取结果不会自动持久化为 State。

因此不建议把“首楼 HTML 表单提交”建立在 Text Extractor 上。

### 4.4 Loom Script / 扩展

Loom Script 和扩展确实可以比普通消息 HTML 做更多事，但必须区分运行环境：

- `client-sandbox` Renderer：可申请 `state.read` 和 `ui.notify`，不能直接写 State；
- `client` / `client-worker` / `server`：可拥有更完整的上下文，但属于用户明确授权的可信代码或后台代码；
- 普通消息 HTML：没有这些业务能力。

如果未来希望“点击提交后自动写入 State”，需要设计为一个单独的扩展或 Loom Script 能力，并明确：

- 用户如何安装；
- 用户如何授权 State 写入；
- 运行在哪个 Scope；
- 读写哪些 JSON Pointer；
- 版本冲突和撤销怎么处理；
- 卡片跨环境导出时这些代码是否随包携带。

## 5. 可选的数据去向

### 方案 A：纯文本档案（推荐作为第一版）

```text
首楼 HTML 表单
  -> 生成 Markdown / 纯文本
  -> 玩家复制
  -> 发送到对话
  -> 模型读取
```

优点：

- 不依赖扩展、State Schema 或权限；
- 角色卡导出/分享最简单；
- 字段可以随时调整；
- 兼容性最好；
- 对 Loom Studio 和普通聊天环境都比较稳妥。

代价：

- 数据不会自动进入 State；
- 不会自动更新玩家资料；
- 不保证跨消息持久化；
- 玩家需要手动复制；
- 无法做严格的结构化校验之外的业务约束。

适合先验证的问题：

- 玩家真正愿意填哪些字段；
- 哪些字段对模型实际有帮助；
- 哪些偏好只是开局一次性信息，不需要进入 State。

### 方案 B：Agent 读取文本后更新 State

```text
表单生成文本
  -> 玩家发送
  -> Agent / 预设识别其中的结构化块
  -> Agent 调用 update_state
  -> 数据进入 Timeline State
```

优点：

- 不需要卡片自带可执行前端代码；
- 可以复用 Agent 的 `read_state` / `update_state` 工具；
- 仍然保留普通消息路径，便于兼容。

代价：

- 依赖当前 Agent 预设是否挂载并启用了相应工具；
- 模型可能提取失败、漏项或改写字段；
- 需要明确 State Schema 和失败后的确认流程；
- 用户消息中的内容不应被无条件当作可信指令。

### 方案 C：Loom Script / 扩展直接写入 State

```text
自定义表单 Surface / Renderer
  -> 授权桥
  -> 指定 State Scope 与 JSON Pointer
  -> Runtime 校验与 CAS 提交
```

优点：

- 交互最直接；
- 可以做真正的持久化、版本校验和撤销；
- 可以针对角色卡提供专门的表单体验。

代价：

- 需要代码、安装、授权、Mount 和生命周期管理；
- 普通消息内 HTML 不能直接复用这套能力；
- 需要处理包内代码导出、版本更新、权限撤销和跨环境可用性；
- 不能把 `client-sandbox` 误认为拥有完整写权限。

### 方案 D：只使用内置玩家资料

只把少量信息放入玩家资料模板的名称和描述，其余内容在对话文本中收集。

优点：

- 最贴近现有产品能力；
- 新故事启动时自动复制到 State；
- 可以使用 `{{user}}` / `{{user.description}}`。

限制：

- 只有名称、描述和头像；
- 模板由“我的”页面管理，不是角色卡首楼表单可写的对象；
- 不适合复杂背景和大量结构化偏好。

## 6. 表单字段决定之前需要回答的问题

### 6.1 数据去向

- [ ] 表单只生成一次性文本，供模型阅读？
- [ ] 表单需要写入 Timeline State？
- [ ] 表单需要更新玩家资料模板？
- [ ] 表单需要跨分支、可撤销、可在变量面板查看？
- [ ] 表单需要同时支持 Loom Studio 和 SillyTavern 等外部环境？

### 6.2 交互方式

- [ ] 首楼里直接显示完整表单？
- [ ] 只用 Markdown 问卷，不依赖 HTML？
- [ ] 首楼表单只负责预览，真正提交靠复制文本？
- [ ] 是否接受额外安装扩展或授权脚本？
- [ ] 是否需要保存草稿、导入/导出档案或跨设备恢复？

### 6.3 数据生命周期

- [ ] 只需在开局时使用一次？
- [ ] 每条回复都要参与提示词？
- [ ] 后续需要修改，并且修改要进入分支历史？
- [ ] 需要随角色卡导出/导入？
- [ ] 需要与玩家资料模板同步，还是每次新故事独立填写？

### 6.4 兼容性

- [ ] 卡片是否需要导出为 `.loomcard.zip` / PNG？
- [ ] 是否需要保留 STBridge 导入兼容？
- [ ] 是否接受首楼 HTML 在其它环境中被当作普通 Markdown 显示？
- [ ] 是否要求移动端填写？
- [ ] 是否要求无 JavaScript 时仍能填写？

### 6.5 内容边界

- [ ] 哪些字段是必填，哪些可以留空？
- [ ] 是否要强制填写安全边界？
- [ ] 是否要区分玩家角色设定和玩家本人偏好？
- [ ] 是否要允许玩家跳过机械数值，只用叙事描述？

## 7. 候选数据域（不是最终字段清单）

以下只是根据角色扮演类卡片的常见需求整理的候选域，用于下一步筛选。**现在不建议直接把它们写成最终表单字段。**

### A. 玩家角色身份

- 姓名 / 称呼
- 代词 / 性别认同
- 年龄或外貌年龄
- 身份、职业、社会位置
- 外貌与第一印象

可能去向：

- 玩家资料 `name` / `description`；
- 首楼生成文本；
- 角色 State 中的玩家组件（需要 Schema）。

### B. 背景、动机与秘密

- 来历
- 来到猩红山脚的原因
- 目标与欲望
- 秘密、旧债或未说出口的事
- 弱点、代价、禁忌
- 随身物件
- 羁绊或牵挂

可能去向：

- 开局文本；
- 角色 State；
- 后续 Lore / 提示词。

### C. 关系与第一幕

- 开场钩子
- 第一幕画面
- 希望重点描写的 NPC 或关系
- 进入故事时正在进行的事

可能去向：

- 一次性提示文本；
- Card 的备选开场；
- 若需要开局状态，再进入 State。

### D. 游玩偏好

- 叙事视角
- 文风与题材
- 节奏
- 回复长度
- 失败与代价的处理方式
- 是否接受角色死亡或不可逆后果
- 情感线倾向
- 主持人代述权限
- 是否允许谜题线索藏在环境描写中

可能去向：

- 作为开局玩家消息的一部分；
- 写入 Preset 或 Card 静态宏；
- 若需要长期保持，则进入 State 的偏好组件。

### E. 安全边界与停止方式

- 不希望出现的内容
- 希望淡出处理的内容
- 暂停/跳过/改写场景的约定

建议：

- 无论最终数据去向如何，都应允许玩家明确表达；
- 不应把“留空”默认解释为“没有边界”；
- 如果写入 State，需要定义只读或受保护字段与更新时机。

### F. 机制与数值

- 属性、技能、资源
- 特殊能力
- 初始物品
- 成长方向
- 随机判定方式

建议：

- 只有在 State Schema、数值规则和写入方确定后再设计这些字段；
- Loom Studio 的 State 本身不是自动跑团规则引擎；
- 如果只是想给模型一段叙事约束，没必要强行做成结构化数值。

---

## 8. 首楼 HTML 表单的硬性设计约束

无论最终选择哪些字段，只要使用首楼 HTML 表单，就建议遵守以下约束：

1. **完整文件开头使用 `<!doctype html>`。** 这样 Loom Studio 的消息解析能稳定识别为完整文档。
2. **不依赖外部资源。** 字体、图片、库都内联或使用 data URI。
3. **不依赖原生表单提交。** 使用按钮和 JavaScript 生成结果，避免被 CSP 的 `form-action 'none'` 拦截。
4. **不依赖父页面、State 或扩展 API。** 普通消息 HTML 没有这些桥。
5. **不依赖 LocalStorage / Cookie / IndexedDB 持久化。** iframe 没有稳定的同源存储上下文。
6. **提供复制回退方案。** `navigator.clipboard` 可能被拒绝，应允许手动全选文本复制。
7. **不要假设输入会保留。** 消息重新渲染或离屏卸载后，表单可能重建。
8. **不要依赖自动保存。** 如果字段较多，必须给玩家一个明确的生成与复制步骤。
9. **避免把大量不必要的数据塞进提示词。** 只收集对当前故事真正有用的信息。
10. **明确区分“玩家角色设定”和“玩家本人元信息”。** 除非确认玩家愿意，不要收集现实身份、账号、联系方式等无关隐私。
11. **对生成文本中的用户输入做清晰分隔。** 避免玩家文本被模型误当成系统指令；可以考虑使用标题、引用块或显式标签包裹。
12. **移动端和键盘操作优先。** 表单控件应有标签、焦点样式和错误提示。
13. **如果使用宏，** 只把它当作开场白生成前的静态/初始值读取；不要把宏当成表单提交后的回写机制。
14. **如果引入脚本或扩展，** 明确写出安装、授权、启用和禁用后的行为。

## 9. 推荐的推进顺序

### 第一步：先确定数据去向

需要从以下选择中先选一个主路线：

- A. 纯文本档案，首楼表单只负责生成内容；
- B. 纯文本档案 + Agent 后续写入 State；
- C. 独立扩展 / Loom Script 表单，直接读写 State；
- D. 只使用内置玩家资料，其他内容放在对话里。

### 第二步：再确定字段

建议按“字段是否真的会影响故事”来筛：

1. 哪些字段只是帮助模型理解玩家角色？
2. 哪些字段需要跨回复持续存在？
3. 哪些字段需要出现在 State 面板或参与分支/撤销？
4. 哪些字段其实只是在第一次提示词里有用？
5. 哪些字段应当由玩家资料或 Card 静态配置提供，而不是重复询问？

### 第三步：确定输出格式

如果采用纯文本方案，可以先设计一种容易阅读、也容易被模型理解的格式，例如：

```markdown
# 开始前背景调查

## 玩家角色
- 姓名：
- 称呼：
- 背景：
- 动机：

## 游玩约定
- 叙事视角：
- 内容边界：
- 主持权限：
```

具体字段仍应等你确认后再定。

### 第四步：制作最小表单原型

先做少量字段，验证：

- 玩家能否顺畅填写；
- 结果复制和发送是否方便；
- 模型是否真的使用了这些信息；
- 移动端 message iframe 的高度和交互是否正常；
- 输入状态丢失的影响有多大；
- 是否值得升级到 State 或扩展方案。

## 10. 当前已确认的项目事实

- 普通消息 HTML 使用隔离 iframe，只授予 `allow-scripts`，不授予同源权限。
- 普通消息 HTML 只与宿主交换高度测量消息，没有业务 Context 桥。
- HTML 预览 CSP 禁止网络、外部字体、媒体和原生表单提交。
- 完整 HTML 文档可由消息解析器识别。
- 开场白会在展示前经过宏渲染。
- 玩家资料只有名称、描述和头像，并在新故事启动时复制到 Timeline State。
- Timeline State 支持结构化数据、分支、撤销和 Agent 工具，但普通 HTML 表单不能直接写入。
- Loom Script 的 `client-sandbox` 仅支持 `state.read` 和 `ui.notify`；写 State 需要其它运行环境和相应授权。
- Text Extractor 的结果不会自动持久化为 State。
- 首楼表单输入不属于可靠持久化状态，消息离屏重建后可能丢失。
